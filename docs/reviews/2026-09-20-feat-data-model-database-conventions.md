## Summary
This branch lays down the full foundational + financial ledger schema (migrations 0002–0006), the PRAGMA/crash-safety plumbing in `db.rs`, and a genuinely thorough test suite (`database_conventions.rs`, `crash_recovery.rs`, `migration_immutability.rs`). The schema itself is well modeled — integer poisha, UTC/business-date separation, defense-in-depth triggers on the ledger tables — and directly traceable to spec 0002's data model. Two real problems remain, though: the connection-integrity check still runs on the hot path on every RPC call (a carry-over from the prior review, not actually fixed), and the clock-guard's forward-jump acknowledgment mechanism described in the spec's own invariants is selected from the database but never used, so there is currently no way to recover from a legitimate forward clock jump.

## Major
### 🟠 `verify_integrity` (PRAGMA quick_check) still runs on every RPC call, `crates/core/src/db.rs:118`
**Problem**: `open_database()` calls `verify_integrity(&conn)` immediately after opening the connection (line 118). `open_database()` itself is called fresh inside `run_ping_transaction()` (line 233) on every single invocation — there is no cached/pooled connection anywhere in the codebase (confirmed: `open_database` has exactly one caller, and that caller runs once per `system.ping` RPC, which fires once per Tauri `rpc` command from `src-tauri/src/lib.rs:12`). The prior review flagged this exact behavior when the call lived in `configure_connection`; the follow-up commit (`abb33e1`) only relocated it one function up — the practical effect (a full-database `PRAGMA quick_check` scan on every user-triggered command) is unchanged.
**Why it matters**: `PRAGMA quick_check` scans the whole database. As student/payment/audit data accumulates, every button click in the UI will pay that scan cost, not just app launch. It also contradicts the spec's own wording for AC-2 ("executes an integrity quick check on startup") and the "Startup health check" row in the Value sourcing table — the current code runs it on every command, not at startup.
**Suggested fix**: Run `verify_integrity` once per process lifetime (e.g., guarded by a `std::sync::Once` / `OnceLock`, or explicitly only from an app-bootstrap path), and separately fix the deeper issue that every RPC call opens a brand-new `Connection` rather than reusing one held for the process lifetime.

### 🟠 Clock-guard forward-jump acknowledgment is unimplemented, `crates/core/src/db.rs:180`
**Problem**: `verify_clock` selects `last_ack_at` from `clock_guard` (`SELECT high_water_at, last_ack_at FROM clock_guard WHERE id = 1`) but only ever reads column 0 (`high_water_at`); `last_ack_at` (and `last_ack_by`) are never read or checked anywhere in the codebase (confirmed via search — `last_ack` appears nowhere else). Spec 0002's key invariant #7 states: "reject forward jumps greater than 24 hours unless acknowledged with `last_ack_by`." As written, there is no code path that ever honors an acknowledgment — a forward jump past `max_forward_hours` is unconditionally rejected, forever, with no way to clear it.
**Why it matters**: A legitimate forward jump (NTP resync after a long-suspended laptop, timezone/DST change, clock correction after a dead CMOS battery) will permanently return `ClockJumpForward` on every future write attempt through this guard, since `high_water_at` is never advanced past the failed check and there's no acknowledgment path to move past it. For a desktop app meant to survive real-world clock weirdness (per spec's own framing), this is a dead end without manual database surgery.
**Suggested fix**: Either implement the acknowledgment check (e.g., allow the jump when `last_ack_by`/`last_ack_at` show a sufficiently recent operator acknowledgment covering it) or, if this is intentionally deferred to a later slice, say so explicitly in the spec's Follow-up section rather than stating it as a already-covered invariant.

## Minor
### 🟡 `trg_charges_no_update` misses NULL ↔ value `period` transitions, `migrations/0006_audit_and_triggers.sql:74-84`
**Problem**: The trigger's `WHEN` clause guards period changes with `(OLD.period IS NOT NULL AND NEW.period IS NOT NULL AND OLD.period != NEW.period)`. Because both sides must be non-null for the comparison to fire, changing `period` from `NULL` to a value, or from a value to `NULL`, silently bypasses the immutability check.
**Why it matters**: `period` is a "key attribute" per the same trigger's own error message ("Charge amounts and key attributes cannot be altered") and per spec AC-4 ("alter key attributes ... posted ... charges"). A one-time charge (`period IS NULL`) could be quietly turned into a recurring-period charge (or vice versa) after creation without tripping the guard.
**Suggested fix**: Use a NULL-safe comparison, e.g. `OLD.period IS NOT NEW.period` (SQLite's `IS`/`IS NOT` handle NULL correctly), in place of the three-part AND.

- Trigger coverage on the ledger tables is now comprehensive and well tested: `database_conventions.rs` exercises audit log, `row_version`, payments, charges, payment allocations, adjustments, refunds, and closed cash days individually, asserting on the exact abort message each time rather than just "it errored."
- `test_transaction_rollback_safety_leaves_zero_trace` and the header-corruption test in `crash_recovery.rs` are solid, meaningful crash-safety tests rather than smoke tests — the corruption test actually flips bytes past the SQLite header and checkpoints WAL first so the corruption is guaranteed to be on-disk before the check.
- Integer-poisha and business-date/UTC-instant separation are consistently applied across every ledger table and are backed by CHECK constraints (e.g., `net_amount_poisha = gross_amount_poisha - concession_amount_poisha`), not just Rust-side conventions.
